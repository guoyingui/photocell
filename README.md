# PhotoCull

当前版本：**1.0.1**。

面向电脑浏览器的 Web 选片工具，使用鼠标与键盘操作。选定装有 RAW+JPG 配对照片的文件夹，快速浏览、收藏、排除，
最后把收藏照片的 RAW 单独复制（或移动）到交付目录。

## 启动

### 前置条件

**Node 22.12+ 最省事**（本仓库在 v22.22 上开发）。硬下限是 vite 8 与 vitest 4 两方
`engines` 的交集：`20.19+`、`22.12+` 或 `24+`——21.x 和 23.x 这两条奇数线不在任何一方
声明的范围里。npm 默认不强制 `engines`，装得上不等于跑得动。

    npm install

`sharp`（缩略图）会拉一份平台相关的预编译二进制，第一次装得慢是正常的。

### 正式启动

    npm start

这一条是两步：先 `vite build` 把前端打进 `server/public/`，再 `node server/index.js`
把它连同 API 一起提供出去。**改完前端要重跑一次 `npm start`**——服务端只负责把
`server/public/` 里已经构建好的东西发出去，它不会自己重编。

浏览器会自动打开服务实际监听的地址，默认是 http://127.0.0.1:5183；如果 5183 被占用（比如已经开着
另一个 PhotoCull 实例），服务会依次往后尝试到 5199，浏览器打开的就是真正绑上的那个端口，
不一定总是 5183。5183–5199 全被占满才会报错退出。

**默认只监听本机**（`127.0.0.1`，不绑 `0.0.0.0`），局域网里连不上，别人拿到这个地址也打不开。
要把选片分享给客户，可在界面「分享」面板显式开启，或使用 `--share` 启动——见下面的《协同选片》。

停服务用 `Ctrl+C`：进程收到 SIGINT 会先关掉所有会话（落盘、断开访客的实时连接）再退出，
`kill -9` 会跳过这一步。

**Windows 上 C 盘以外的盘符会被枚举出来**，照片一般不在系统盘。文件夹选择器里
`D:\`、`E:\` 和挂上的网络驱动器都是可浏览的根。探测逐个盘符做，未插盘的光驱、
断开的网络驱动器会被超时跳过，不会把选择器卡住。

**「系统选择文件夹…」**打开运行 PhotoCull 那台电脑的系统窗口，选好后直接开库。
macOS、Windows 支持；Linux 需要图形桌面及 zenity 或 kdialog。不可用时继续使用页面目录浏览器。
远程管理不提供系统窗口入口，避免把窗口打开在另一台电脑上。

**可以拖入文件夹**：系统提供真实 `file://` 路径时直接打开；多数浏览器只提供目录名称，
此时匹配最近目录或当前目录作为候选，仍需点击打开。不会把同名目录当成同一个目录。

### 带开关启动

开关要经 `--` 转交给 node，npm 会把 `--` 后面的东西原样接到脚本命令的末尾：

    npm start -- --share
    npm start -- --share --admin-token=<自己生成的随机串>

这两个开关各自的含义、代价和适用场景在《开启分享》和《管理员身份怎么判定》两节里，
**别只照抄命令**。认不出的开关一律被忽略，落点是不分享、不开令牌。

### 开发模式（前端热更新）

    npm run dev

一条命令起两个进程：`vite`（5173，改前端即时生效）和 `node --watch server/index.js`
（5183，改服务端自动重启）。

**要访问的是 http://127.0.0.1:5173**，不是自动弹出来的那个 5183。服务端不知道自己此刻
是被开发模式起来的，照常把 5183 打开在浏览器里——那一屏是上次 `npm start` 留下的构建
产物，跟你正在改的源码没有关系；刚 clone 完、一次都没构建过的话它是一句
`Cannot GET /`，那不是坏了，是 `server/public/` 还不存在。（`--watch` 每次重启进程都会
把这个标签页再唤起一次，改服务端文件时尤其烦人。）

5173 的 `/api` 请求由 vite 代理到 5183，所以两个进程必须都活着。

`npm run dev -- --share` **不管用**：`--` 后面的东西接的是 `concurrently` 的命令行末尾，
`--share` 会被它当成"第三条要执行的命令"，服务端一个字都收不到。开发模式下要开分享，
绕开 npm 脚本直接起服务端：

    node server/index.js --share

（这样只有服务端，另开一个终端跑 `npm run dev:web` 补上前端热更新。）

### 脚本一览

| 命令 | 做什么 |
|---|---|
| `npm start` | 构建前端 + 起服务。日常用这条 |
| `npm run dev` | vite 5173 + `node --watch` 5183，两个进程 |
| `npm run dev:web` / `npm run dev:server` | 只起其中一个 |
| `npm run build` | 只构建前端到 `server/public/`（该目录是产物，已被 gitignore） |
| `npm test` | 跑一遍全部单元测试后退出 |
| `npm run test:watch` | 测试 watch 模式 |
| `npx tsc --noEmit` | 类型检查。只覆盖 `web/src`，服务端是纯 JS 不参与 |
| `npm run desktop:dev` | Tauri 窗口 + 本机 Node 服务，用来看桌面壳 |
| `./scripts/build-desktop.sh` | 打 macOS `.dmg` 和 Windows NSIS 安装包到 `deploy/dist/` |

## 桌面安装包（Windows / macOS）

浏览器那条路还在：`npm start` 照常。桌面安装包是同一份 Node 服务，外面加了一层 [Tauri](https://tauri.app) 窗口，用户不用自己装 Node、也不用记端口。

本机是 macOS 时：

    ./scripts/build-desktop.sh          # 先打 Mac，再交叉编译 Windows
    ./scripts/build-desktop.sh mac      # 只打 PhotoCull_*.dmg
    ./scripts/build-desktop.sh win      # 只打 PhotoCull_*-setup.exe

产物在 `deploy/dist/`。Windows 包是在 Mac 上用 `cargo-xwin` + NSIS 交叉编的，**没有代码签名**，SmartScreen 会报警，需要点「更多信息 → 仍要运行」。macOS 包同样没有 Apple 开发者签名，从网盘/浏览器下下来的 `.dmg` 会被 Gatekeeper 拦住——本地 `tauri build` 打出来的可以直接打开；发给别人时，让对方按住 Control 点图标选「打开」。

包里自带一份 Node 22 和对应平台的 `sharp` 二进制，逻辑和 `deploy/build-linux.sh` 一样：缩略图那份原生模块按目标操作系统交叉安装，不会把本机的 darwin 二进制打进 Windows 包。

协同选片桌面版默认关掉，和 `npm start` 一样。普通启动后可在「分享」面板开启、关闭局域网访问。

## 白色与黑色主题

文件夹选择页和选片页顶部都有主题切换按钮。首次打开跟随系统明暗设置，点击
「白色主题」或「黑色主题」后立即切换，并在当前浏览器记住选择，刷新、换文件夹
后仍然生效。主题是本机显示设置，不会改变照片、选片数据或其他访客的界面。

## 鼠标与键盘怎么标记

收藏后在图片右下角显示 `★`，排除后显示 `✕`；照片边框表示当前选区。
点击照片选中一张，双击或按 `Enter` / `Space` 打开大图。

- 拖动鼠标框选多张照片；`⌘` / `Ctrl` 点选增减选区；`Shift` 点选或方向键连续选择。
- `⌘A` / `Ctrl+A` 选择当前筛选下的全部照片，包括折叠连拍组中的成员。
- 选中后，顶栏显示收藏、排除、取消标记，以及摄影师专用的隐藏按钮。
- 批量操作完成后清空选区。键盘对单张标记时会前进到下一张。
- 协同标记或隐藏使照片离开当前筛选时，自动移出选区；正在显示它的大图或对比会关闭。
- 顶栏常驻「撤销」「重做」，分别支持 `⌘/Ctrl+Z`、`⌘/Ctrl+Shift+Z`；Windows 也可用 `Ctrl+Y`。
  历史保留当前会话最近 50 次标记操作，批量标记算一步；切换目录或重新载入后清空。
  隐藏通过「已隐藏」页签取消，不进入标记撤销历史。

左侧目录的 `✕` 会整批排除该目录下的照片，不受当前标签页影响。
再次点击会取消整个目录的标记；恢复之前混合的收藏/排除状态应使用「撤销」。
这些操作只修改标记，不删除文件。

本机浏览器记住每个照片目录上次选片的位置。重新打开时自动定位并展开所在连拍组，
不会恢复之前的批量选区；已经消失或隐藏的照片不会成为续选目标。

### 大图操作

大图下方常驻上一张、下一张、收藏、排除和取消标记按钮，只读访客只有浏览操作。
「100%」读取完整 JPG 后按图片像素与屏幕 CSS 像素 1:1 显示；「贴合窗口」恢复完整构图。
滚轮以鼠标位置为中心缩放，放大后左键拖动平移。信息面板开关与窗口大小变化会重新计算显示范围。
纯 RAW 的 100% 基于内嵌 JPEG 的分辨率，不能替代 RAW 解码后的全分辨率检查。

### 照片信息与查找

选中照片后点击「照片信息（I）」或按 `I`，右侧显示 RAW/JPG 文件名、相对目录、拍摄时间、ISO、光圈、快门和焦距。
大图中也可打开信息面板。缺失参数显示「未知」，文件时间回退会明确标为「文件时间」。

网格上方的「文件名搜索」支持编号、完整文件名或相对路径，不区分大小写。
输入后按回车或点击「定位下一张」依次定位匹配照片；同名文件会按各自目录分别保留。
搜索会与目录、标签页、成员和拍摄参数筛选共同生效；找不到时可用「清除筛选」恢复全库视图。
ISO、光圈、快门、焦距可以组合筛选，也可筛选参数未知的照片。元数据载入过程中结果会更新。

### 我的浏览进度

「还没看」「已看过」「看过但未标记」独立于收藏和排除。打开大图、进入双图对比，或主动标记照片时记为已看；
仅滚动网格、框选或文件名定位不会自动记为已看。可对选区点击「记为已看」（`V`）或「恢复未看」。
在「还没看」筛选中，正在预览的照片保留到离开预览，随后从该筛选中移出。

进度条统计整个照片目录中未隐藏的照片。每位成员拥有独立进度，保存在照片目录中，重新打开应用后仍在；
只读访客也能记录自己的浏览进度，但不能修改照片标记、其他人的进度或连拍设置。
访客使用原有身份回来可继续进度，创建新身份则从新的进度开始。旧版本已有的标记不会自动当成已看。

### 隐藏

废片太多的时候，把它们从眼前挪开比逐张标记更省事。多选之后顶栏操作条上有「隐藏」，
键盘是 `H`。

- **只有摄影师能隐藏**，客户那一侧连按钮都不渲染。
- **隐藏对所有人生效**：藏起来的照片在客户浏览器中也不再出现，不是只有你看不见。
- **已经标记过的照片不能隐藏。** 一批里混着几张标过的，那几张会被跳过、其余照常
  隐藏，并提示「N 张因为已有标记被跳过」——不会因为一张而整批失败。
- 藏起来的照片都在第五个页签「已隐藏」里（快捷键 `5`，只有你看得见）。那一屏的
  格子上是一个 `↩` 取消隐藏按钮，**不再显示 `✓`/`✕`**：在这里打标记会让照片自动
  取消隐藏、当场从眼前消失，把这个后果藏在一个看起来只是「标记」的按钮后面是误导。
- **它不删文件。** 和排除一样，隐藏只是一个标记，磁盘上一张都不会少。

## 刷新

顶栏的「刷新」原地重新扫描当前文件夹。选片过程中照片被移动、删除、或者又拷进来
几张时用它。

- **不退回文件夹选择器**，旧网格一直显示到扫完为止。这是它和「换文件夹」最重要的
  区别。
- 扫完会提示这次少了几张、多了几张。
- **消失的照片，它的标记仍然留在 `marks.json` 里**——照片挪回来就还在。
- 只有摄影师能刷新（`POST /api/library/refresh` 是 admin-only），但**换掉的是
  所有人正在看的那一份**：客户那一侧会自己重拉，不用他刷新页面。他正开着大图
  看的那张要是没了，大图会关掉——总比停在一张永远显示不出来的照片上强。
- **扫描失败时旧的资产表一个字段都不动**，只多一条错误提示。这和打开文件夹失败
  不一样：那时手上没有任何可用数据，而这里已经有一份能用的。
  这种情况下客户那一侧也不会重拉——服务端保留的还是同一份表，拉了也一样。

## 数据存放

选片进度与缩略图缓存都写在照片文件夹下的 `.photocull/`：

    <照片文件夹>/.photocull/
    ├── marks.json        标记与设置
    ├── marks.bak.json    上一次的备份
    ├── review.json       按成员保存的浏览进度
    ├── selections.json   客户提交、整体与单张备注、确认状态
    ├── annotations.json  星级、颜色标签、关键词与后期阶段
    ├── exports/          导出任务、逐文件结果与重试关联
    ├── thumbs/*.webp     缩略图缓存
    └── raw-previews/     RAW 内嵌 JPEG 预览缓存

文件夹拷到别的机器，选片进度跟着走。删掉 `.photocull/` 即完全重来。
`review.json` 中是成员 id 与照片 id；`exports/` 中包含导出目标路径、结果和错误说明。
浏览续选位置仍由当前浏览器按照片目录记住，不包含在这些文件中。

`marks.json` 里除了标记和设置，还有两张平行表：`hidden`（已隐藏照片的 id）和
`contrib`（**每张照片上每个人各投过什么票**，取消标记时靠它回退到上一个人那一票）。

`contrib` 里存的是 `userId`（`u_` 开头的随机串）和时间戳，**不含昵称、不含令牌**。
但它确实记录了「有几个不同的人参与过这次选片、各自选了哪些」——**把照片文件夹交给
客户时，这份信息会跟着走**。

如需清理标记中的归属，`contrib` 和 `marksMeta` **两张表都得删**：`marksMeta` 里同样带
`userId`，而且删掉 `contrib` 之后开库会拿 `marks` + `marksMeta` 把它回填回来。
两张都删之后标记本身还在，代价是角标不再显示归属、取消标记也不再回退到上一个人
那一票（见《当前行为里几条必须先知道的事》第 8 条）。
个人浏览进度中的成员 id 独立保存在 `review.json`，不会随标记归属的清理而删除。
`marks.json` 的 `finalMarks` 单独记录摄影师最终决定，覆盖有效标记但不改变各人的原始意见。
`selections.json` 包含客户备注，随照片目录移动时也会带走；这里只按成员 id 保存，不保存登录令牌。

点击「设置… → 清理当前目录的预览缓存」，查看缓存大小并清理缩略图、RAW 预览。
源照片、标记、浏览进度、客户提交、后期信息和导出历史会保留；之后按需重新生成预览。

分享链接、访客账户和审计日志**不在这里**，在你自己家目录下的 `~/.photocull/`——
它们是你的经营记录，不该跟着照片文件夹一起打包发给客户。见《协同选片》。

## 连拍分组

相邻两张同时满足「拍摄时间差 ≤ 阈值」「同一机身」「时间不是从文件 mtime 推断的」
才归为一组。分组在前端计算，不发请求。

点击顶栏「设置…」调整连拍间隔，范围 0–10 秒，默认 1.0 秒。
保存前会预览预计的连拍组数；保存成功后更新分组，并写入当前目录的 `.photocull/marks.json`。
只有摄影师能修改，已连接的访客会同步更新，断线重连也会补齐设置。
仍支持旧目录中的有效阈值；缺失或非法值使用默认值。

## 双图对比

用 `⌘` / `Ctrl` 点选两张照片，点击顶栏「对比」或按 `C`。
左侧固定参考图，右侧通过按钮或方向键更换候选；滚轮和拖拽同步控制两张图的缩放与平移。
「交换位置」可把当前候选换成参考图，「恢复贴合」重置视图。

两侧都有独立的收藏、排除、取消标记按钮。`P` / `X` / `U` 只操作右侧候选，
不会操作进入对比前的批量选区。`Esc` 退出；只读访客可以比较但不能修改标记。
刷新或筛选使任一对比照片不可见时，对比自动关闭。

## 客户提交与确认

新建分享或编辑分享时，可设置每位客户的选片上限；留空表示不限。
客户页显示「我已选 28 / 30 张」，按客户自己的收藏计数，其他成员或摄影师的决定不影响数量。
可填写整体备注，也可在照片信息面板保存单张备注。未保存备注或标记仍在保存时不能提交。

客户确认提交后，收藏清单保存为快照并锁定自己的标记和备注；刷新网页、重启服务后仍锁定。
摄影师从「客户提交…」查看清单与备注，确认提交或重新开放修改。确认提交不自动替摄影师决定最终名单。
重新开放后客户可以继续修改并再次提交。只读访客不能提交或修改备注。

## 多人意见与最终名单

摄影师的「客户意见」栏支持共同收藏、收藏与排除有争议、至少两人收藏三个筛选。
共同收藏表示至少两位客户收藏且没有客户排除；未表态不算赞同，不计摄影师的一票。
信息面板显示各人的原始意见。隐藏客户标记的分享仍不会把其他客户的意见交给访客。

选区可确认为最终收藏、最终排除，或清除最终决定。只处理当前仍可见的选区。
最终决定单独保存，客户后来投票不改变它，也不修改客户已提交的清单。
「全库最终收藏」导出遵循最终决定；清除决定后恢复到原来的协同有效标记。

## 星级、标签与后期衔接

摄影师在照片信息面板设置 0–5 星、颜色标签、关键词及初选／精修／交付阶段；选区可批量设置。
批量表单中的「保持原值」保留各照片原值；勾选替换关键词且留空会清除关键词。
照片网格显示已设置的星级和阶段；后期筛选可与文件名、参数、目录、成员及意见筛选叠加。
这些信息是摄影师的库级数据，访客只能查看与筛选。

「后期 → 导出 XMP…」支持全库最终收藏、当前筛选的照片和当前可见选区，仅处理带 RAW 的照片。
下载 ZIP 保留相对目录，并按 RAW 主名生成 `.xmp`；同目录同主名的多种 RAW 共用一个 sidecar。
解压后放在对应 RAW 旁，再由修图软件读取元数据。此下载不改源照片或磁盘上已有的 XMP。

字段使用 `xmp:Rating`、`xmp:Label`、`dc:subject`；颜色文本为 Red / Yellow / Green / Blue / Purple，
需要与目标软件的标签设置一致。阶段同时保存为 `PhotoCull/初选`、`PhotoCull/精修`、`PhotoCull/交付` 关键词。
摄影师最终决定另存于 PhotoCull 自定义字段，不替换星级，也不承诺转换成各软件的收藏旗标。
已有修图 sidecar 请先备份并合并，避免解压覆盖已有修图参数。

实现按 [Adobe XMP 字段定义](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp/)生成。
Lightroom Classic 的读取方式参考 [Adobe 元数据操作说明](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/advanced-metadata-actions.html)。
目前完成格式与下载测试，尚未在真实 Lightroom/Capture One 中验收；DNG/JPG 等内嵌元数据格式需要单独验证。

## 纯 RAW 预览

有配对 JPG 时优先使用 JPG；纯 RAW 尝试沿 TIFF 目录提取内嵌 JPEG，选择较大的预览并保留方向。
当前处理标准 TIFF 的 JPEG 偏移标签或单段 JPEG strip，可用于具有这种结构的 CR2、NEF、ARW、DNG 等文件。
不会解码 RAW 像素，不保证所有型号或所有同扩展名文件可预览；CR3 等其他容器暂不支持。
未找到有效预览时显示占位，信息面板说明原因，建议补充配对 JPG。

预览按源文件路径、大小、修改时间缓存，源文件变化后生成新预览。
已用人工构造的大小端 TIFF 验证目录解析、尺寸、方向、缓存和损坏文件边界；真实机身样张验收仍待执行。

## 导出

- **导出只有管理员能做，访客永远不能**——这是硬编码，不是某个可以打开的开关。见《协同选片》
- 默认只复制选定范围内的 RAW，保留子目录结构。面板明确显示本次范围与文件数：
  - **全库最终收藏**：导出所有人的最终有效收藏。
  - **当前筛选中的收藏**：遵守目录、标签页、成员、文件名、参数、浏览状态、意见和后期筛选，包含折叠连拍组中的成员。
  - **指定成员的收藏**：依据该成员自己的意见，即使后来被其他成员改为排除也能导出。
  - **手动选中照片**：导出当前选区，不要求先收藏，不改变原有标记。
- 有多张选区时默认导出选区；否则优先使用当前目录/标签筛选或成员筛选。
  可在执行前改成其他范围。服务端使用实际资产与标记重新计算，移动确认数也按这个范围核对。
- 可选同时复制 JPG、平铺到单层、生成 `manifest.csv` 与 `rejected.txt`
- 移动模式严格按「复制 → 校验大小 → 删除源文件」执行；界面上必须手动输入待移动的
  文件数才能确认，服务端收到请求后会独立重新统计一遍要处理的文件数，
  和前端提交的确认值对不上就拒绝执行（400），不会因为前端算错或被绕过而误删源文件
- 收藏但没有 RAW 的照片会在结果里单独列出，不会静默丢失
- `manifest.csv` 每行对应一个已收藏资产的 RAW 文件，列为：
  `assetId, mark, rawFile, jpgFile, captureTime, exportedAs, status`。
  `status` 取值 `exported`（本次写入）/ `renamed`（撞名后改名写入）/
  `skipped`（目标位置已有同大小同 mtime 的文件，本次未写入）——
  这一列是后加的：早先的版本会把跳过的文件也算作"已导出"，
  实际上那些文件是更早一次导出就已经在目标目录里的，本次并没有产生新的复制/移动。

### 导出历史与失败重试

点击「导出… → 导出历史」，查看当前照片目录的历史任务、逐文件结果，或下载 CSV 清单。
记录保存在 `.photocull/exports/`，应用重新启动后仍可读取；更早记录通过「加载更早的记录」查看。
已有版本在升级前完成的任务没有这些记录，不会自动补生成。

「重试未完成文件」只处理失败、取消或中断后未完成的文件，沿用原来的 JPG 子目录和平铺设置，允许修改目标目录。
例如 RAW 已成功、JPG 失败，重试只处理 JPG，之后修改收藏状态也不会改变这份重试清单。
重试默认复制；选择移动时必须重新输入待重试文件数，服务端独立核对，仍按复制、校验、删源的顺序执行。
重试成功会关联回原记录，相同失败项不会再次进入重试。

「已送达，源文件未删除」不自动重试，请根据清单核对两端文件。无 RAW 的照片需补齐 RAW 后重新扫描并发起新导出。
如果只有交付目录内的 manifest 写入失败，仍可从导出历史下载逐文件 CSV 清单。
运行中的任务可以在历史中查看进度和取消；服务重启后未结束的任务显示为「已中断」，不会自行恢复移动。

## 协同选片（把选片分享给客户）

摄影师本机是**管理员**，身份由「请求来自回环地址」证明；客户是**访客**，身份由「持有分享链接
下发的用户令牌」证明。各人的原始意见保存在同一份 `marks.json` 中，共同形成浏览与导出的有效标记。
客户提交的收藏快照与摄影师的最终决定分别保存，方便比较意见和确认最终名单。

### 开启分享

普通启动后，打开「分享」面板，点击「开启局域网分享」。本机监听仍在原端口，
分享使用独立端口（通常 5184），实际地址与端口以面板显示为准。选择可连通的网卡地址后复制链接，
也可点击「二维码」展示同一链接；二维码在本机生成，不调用外部二维码服务。
「关闭局域网分享」关闭这个监听并断开客户连接，本机选片和导出继续。这个开关不跨服务重启自动开启。

命令行方式仍可使用：

    npm start -- --share

加了 `--share` 时直接监听 `0.0.0.0`，局域网内可达；普通启动时只监听本机，直到在面板主动开启分享。
命令行分享启动时终端会打印检测到的网卡地址和说明，请核对后再发链接。
命令行分享保留原有端口和部署方式，由启动参数控制；此模式关闭服务即可结束网络访问。

认不出的开关一律被忽略，落点是**不分享**。`--shar` 打错一个字母的结果是"没开成分享"
（看启动横幅就知道），不会反过来悄悄把一台能删 RAW 的机器挂上局域网。

浏览器打开的始终是回环地址 `http://127.0.0.1:<端口>`——你自己这台机器上，回环即管理员。
给客户的链接要用横幅里列出的局域网地址，或者直接用界面上「分享」面板里的复制按钮。

**开着 `--share` 期间这台机器上跑着一个能读你本机任意路径、能在移动模式下删除 RAW 的服务。
用完请关掉这个进程，不要让它一直挂着。**

#### 只认地址，不认域名

服务端会校验每个请求的 `Host` 头，只接受这几种写法：`localhost`、`127.x.x.x`、`[::1]`、
横幅里印出来的那几个网卡地址，以及 `*.local` 的 Bonjour / mDNS 名字。
别的一律 403 `bad-host`。

这不是洁癖，它挡的是 **DNS 重绑定**：任何一个你随手打开的网页，只要把自己的域名指向
`127.0.0.1`，浏览器就会**真的**连到你本机这个服务上——源地址是回环，服务端如实把它
当成你本人，而那个页面又和本服务同源、读得到每一个响应。也就是说，一个你只是路过的
网站可以借你的浏览器浏览你整块硬盘、逐张下载原图，并在移动模式下删掉你的 RAW。
`Host` 是唯一能识破它的信号：浏览器发出去的永远是地址栏里那个名字，不是它解析出的 IP。

`*.local`（`某某的-MacBook.local:5183`）是这份名单里唯一按后缀放行的一类，也确实是
唯一的例外。放它进来不削弱上面那段推理：`.local` 由 RFC 6762 保留给 mDNS，不走 DNS
层级，也不是根区里可委派的顶级域——**没有人能去注册一个 `.local` 名字**，而重绑定
的全部前提正是"攻击者拿自己的权威 DNS 服务器改答案"。剩下的风险只有同一个局域网里
的 mDNS 抢名，可那种人本来就能直接打你的 IP，用不着绕这个名字。

注意后缀必须落在末尾：`x.local.evil.com` 这种把 `.local` 塞在中间的**照样 403**，
它是攻击者注册得到的真域名。

没有 `Host` 头的请求（HTTP/1.0、某些健康检查）照常放行——那种请求不可能来自浏览器，
也就不可能是这种攻击。

### 默认是 HTTP 明文，同网段可以被抓包

传输没有加密。同一个局域网里的人可以抓到照片本身，也可以抓到访客的会话 Cookie
（Cookie 里就是那枚用户令牌，等价于密码）。这是我们**明确不防**的一类威胁，
不是还没做完——目标场景是影棚、家里这类可信网络。

不内置 TLS、不内置隧道、不内置端口映射。要跨互联网用，请自己上 Tailscale / Cloudflare Tunnel /
frp 之类，并且**必须**给它配上 HTTPS，否则用户令牌就是在公网上裸奔。
把这个进程推上公网应该是你显式做出的决定，不该由一个默认值替你做。

### 这条链接就是密码

分享链接形如 `http://192.168.1.23:5183/s/<43 个字符的随机串>`。**没有第二道验证**：
拿到链接的人打开就能看图，转发到微信群里，群里每个人都能进。这既是功能
（客户不用注册、不用记密码，把链接丢给伴娘就行），也是你必须先理解的风险。

你手上有四个闸门，都在服务端强制，改完立刻生效：

| 闸门 | 作用 | 拿到链接的人会遇到什么 |
|---|---|---|
| **有效期** | 到点后链接作废 | 统一 404「链接不存在或已失效」 |
| **撤销** | 随时手动作废 | 同上，文案一模一样 |
| **人数上限** | 限制这条链接下能建几个账户 | 403「参与人数已达上限」 |
| **关闭新成员** | 只让已经建过号的人进 | 403「这条链接已停止接纳新成员」 |

失效的链接一律回同一句 404，不区分"不存在"/"已过期"/"已撤销"——不告诉外面的人
哪个 token 是真的存在过的。真实原因照常进审计日志，你在 `/admin` 里看得到。
猜 token 也不划算：按来源地址限流，60 秒内 20 次失败就开始回 429。

### 三个入口，两种角色

| 地址 | 谁能进 | 是什么 |
|---|---|---|
| `/` | 仅管理员 | 本地选片全部功能 + 分享面板 |
| `/s/<token>` | 任何拿到链接的人 | 访客选片界面 |
| `/admin` | 仅管理员 | 管理后台：分享 / 用户 / 审计日志 |

访客有两种角色，可以在 `/admin` 里逐人切换，改完通过 SSE 立刻推给对方：

- `editor`：能看图、能标记
- `viewer`：只能看。这一条由**三道**共同兑现，不是只把按钮藏起来：服务端对写请求
  一律 403；界面不显示标记操作和撤销/重做按钮，但保留浏览与对比；`P` / `X` / `U` 共用的
  标记入口内部还有最后一道判断。改权限是即时的，管理员一改，对方屏幕上这些入口
  当场消失

**两种角色都永远不能导出。** 目录浏览（`/api/fs/*`）、开库关库、库级设置（连拍阈值等）、
导出和移动，全部仅限管理员。这是硬编码，界面上找不到、配置里也没有一个开关可以放开它——
最坏的后果是删掉不可再生的 RAW，所以不设"信任的客户"这一档。

### 管理员身份怎么判定，以及反向代理这个坑

判定只看 TCP 源地址是不是回环，**绝不读 `X-Forwarded-For`**（那是客户端可以随便写的请求头）。
想从其他电脑管理，用 `--admin-token`：

    npm start -- --share --admin-token=<自己生成的随机串>

没有密码登录——再造一套凭据管理不如复用"能物理接触这台机器"。

**设了 `--admin-token` 之后，回环本身就不再算管理员了。** 这个开关的语义是"我前面有东西了，
从现在起只认令牌"——它是回环判定的**替代**，不是额外多开的一条通道。
所以**只在你确实需要它的时候才加这个开关**：单机选片不要加。

#### 浏览器怎么用这个开关

令牌有两条通道，浏览器只走得通第二条：

| 通道 | 谁用得上 |
|---|---|
| `X-PhotoCull-Admin: <同一个串>` 请求头 | curl、Postman、脚本 |
| `GET /admin-login?token=<同一个串>` 换来的 Cookie | **浏览器**，用于电脑浏览器 |

原因很简单：**浏览器没有办法给导航请求加自定义请求头**。地址栏里敲一个网址、
点一个链接、扫一个二维码，发出去的都是导航请求，那个头挂不上去。

所以启动时横幅里会打印一条**登录 URL**，长这样：

    http://192.168.1.23:5183/admin-login?token=<你的令牌>

在另一台电脑（或者本机）的浏览器里打开它，服务端校验通过后会种一枚
`HttpOnly; SameSite=Lax; Path=/` 的 Cookie，再把你 302 跳回首页——
**令牌不会留在地址栏里**，之后每个请求浏览器自动带上那枚 Cookie，你就是管理员了。
Cookie 不设过期时间，浏览器关掉就没了；进程重启换一个令牌，旧 Cookie 也就自然失效。

`--share` 时横幅会把本机地址和每个网卡地址的登录 URL 都列出来（不开分享时只列本机的，
因为那些局域网地址此刻一个都连不上）。令牌带错、或者根本没配这个开关时，
这条路径一律回 404，且两种情况的响应一模一样——不告诉外面的人这台机器有没有开这个开关。

**这条 URL 等同于管理员密码，用完就丢。** 它是终端里唯一会出现令牌值的地方
（不打印它，这个开关就没有任何浏览器用得了）。别截图、别贴进聊天窗口、别存成书签。
诚实说明残余风险：它走的是 HTTP 明文，同网段可以抓包；它也可能进浏览器的"最近访问"建议，
或者进你前面那层反向代理的访问日志。要换令牌就重启进程，换一个新串。

**把 PhotoCull 放在反向代理（nginx / Caddy / Traefik）后面之前请先读这一段。**
危险的方向取决于代理跑在哪台机器上，而两个方向正好相反：

- 代理在**另一台机器**上：所有请求都不是回环，管理员判定整个失效（关门）。
  这种情况必须用 `--admin-token` 才管得了。
- 代理和 PhotoCull 在**同一台机器**上（nginx / Caddy 反代 localhost，最常见的部署形态）：
  每一个转发过来的请求源地址都是 `127.0.0.1`——如果只看源地址，**每一个访客都会变成管理员**，
  能浏览你的整块硬盘、能触发导出、能在移动模式下删你的 RAW（开门）。

同机那一种现在有两条防护（见 `server/lib/actor.js`）：

1. **配了 `--admin-token` 之后，回环本身不再算管理员，只有带对令牌的请求才算。**
   它不再是一条"额外"通道，而是替代——这正是以前救不了的原因。
   配上它之后你自己也得走一次上面那条 `/admin-login?token=…`，浏览器才认得你是管理员。
2. **请求带任何转发头（`X-Forwarded-For` / `X-Real-IP` / `Forwarded`）时，一律不给回环管理员身份。**
   nginx、Caddy、Traefik 的默认配置都会加这些头，所以默认配置下这条就够了。
   攻击者加这些头只能把自己降级，没法用它提权。

**但仍然不要这么部署。** 一个被显式配置成**不加任何转发头**的同机代理，转发进来的请求
跟你自己在本机点开的没有任何区别，两条防护都看不出来。真要用代理，请务必同时配上
`--admin-token`——那是唯一不依赖"代理有没有加头"的那一条。
`--share` 且没配令牌时，启动横幅会把这段话再说一遍。

### 协同数据存在 `~/.photocull/`

    ~/.photocull/
    ├── shares.json                  全部分享的索引（含链接令牌）
    └── shares/<shareId>/
        ├── users.json               这条分享下的用户（含用户令牌）
        ├── events.jsonl             审计日志，只追加
        └── events.1.jsonl           轮转出来的旧日志，最多留 3 代

放在这里而不是照片文件夹里，有三个原因：访客带着 token 上门时还没有任何库被打开，
服务端必须先由 token 反查出该开哪个文件夹；客户的账户表和行为日志是你的经营记录，
不该跟着交付物一起发出去；照片有可能在写保护的 SD 卡上，协同层的写入不该因此失败。

**这个目录和它下面的内容创建时权限设为 `0700`**（mkdir 之后还会再 chmod 一次，
免得被 umask 削掉），因为 `shares.json` 和 `users.json` 里的令牌等价于密码，
同一台机器上的其它账号不该读得到。把这两个文件发给别人等于把链接发给别人。

日志单个文件超过 16 MB 就轮转，保留 3 代，更老的直接丢弃。

### 昵称不是凭据

访客点开链接后自己填一个昵称建号。同一条分享内昵称唯一，重名直接 409 让他换一个，
**不自动加后缀**——把两个人的操作显示成相近的名字会直接毁掉审计的价值。

判定顺序是「先查昵称是否被占用，再看允不允许建新号」。反过来的话，
「关闭新成员」就变成了「凭昵称即可进入某人的账户」：任何拿到链接的人打出「新娘小林」
都能继承她的全部操作历史。所以：**昵称只是显示名，令牌才是凭据。**

由此带来一个你迟早会碰上的情况：**一位老客户清了浏览器数据（Cookie 没了），
而这条分享已经关闭了新成员。** 他现在进不来了——
用原来的昵称会撞上 409（他自己的账户还在，占着这个名字），换个昵称会撞上 403。
处理办法是在 `/admin` 里：

1. 把这条分享的「允许新成员加入」重新打开。**只做这一步他就能进来了**，
   但得换一个昵称，新账户是新的 id，跟他以前的操作历史对不上号。
2. 想让他还用原来那个名字，就在打开开关之外，再把他那条旧的用户记录删掉——
   删掉之后昵称才会被释放。注意这仍然是一个**全新的账户**（新 id、新令牌），
   旧日志里的记录指向的是那个已经被删掉的 id。

（只删记录、不重新打开开关是没用的：昵称是空出来了，但下一道闸门照样 403。）

### 客户能不能看到彼此的标记

每条分享上有一个开关：**让客户看到彼此的选片标记**。新建表单里有复选框，已经发出去
的链接在分享列表那一行上有「隐藏客户标记 / 公开客户标记」按钮。

- **默认公开**，也就是改造前的行为。升级不会悄悄改变一条已经发出去的链接的表现。
- **关掉之后，每位客户只看得见自己的选择和你的选择**，看不见别的客户选了什么。
  她自己改过的那张显示成她改过的样子；她没碰过的显示你的那一票。
- **这个开关只影响点链接的客户，不影响你**。你这一侧永远看得到全部，也能按人筛。
- **改完立刻生效**，不用等客户刷新：服务端会把这条分享上在线的客户全部推一遍。
  两个方向都推——关掉时把别人的标记从她屏幕上撤走，重新打开时把它们放出来。

**过滤是服务端做的，不是前端藏起来。** 关掉之后，`GET /api/library/marks` 的响应里
根本不存在别人那一票，整张 `contrib` 也不下发（那张表只给你）。前端过滤只是把东西
藏起来，数据照样发到了对方的浏览器里，打开开发者工具就看得见「妈妈收藏了哪些」。

**连广播的时机都过滤掉了。** 别人标记时如果这次改动不影响「她看到的那个值」，
她那条连接**收不到任何一帧**。只把值替换掉、照发不误是不够的：她那一格在别人操作的
瞬间重渲染一次，等于告诉她「刚才有人动了这张」。

### 按客户维度筛选

成员条上的头像可以点。点一下只看这个人碰过的照片，再点一下取消。**只有你能点**——
客户那一侧服务端根本不下发别人的 contrib，筛出来必然是空的，所以那里干脆不渲染成
按钮。

判据是**那个人自己那一票**，不是这张照片此刻的有效标记。这两者经常不一样：一张
新娘收藏、后来被妈妈改成排除的照片，有效标记是妈妈的排除，但它仍然属于「新娘收藏过
的那些」。能回答「新娘收藏过哪些」而不只是「最后一次是谁改的」，正是这个入口的用处。

**筛了人之后「全部」不再等于整库**，而是等于「他碰过的」，也就是收藏 + 排除。这不是
bug——如果「全部」不受筛选影响，这个入口就是个摆设。所以那一格的文案也跟着换成
「新娘碰过的 N」，不留一个叫「全部」、数字却比库里少的格子让人自己猜。

**「已隐藏」那个页签忽略筛的是谁**：隐藏是你的操作，没有客户维度。

筛选**只改变你看到什么，不改变标记的身份**。筛着「新娘」的时候按 `P`，记进 `contrib`
的仍然是你自己。没有任何入口能代替别人投票。

成员条上显示谁：**在线的一律显示；离线的只要标过照片就继续留着**（头像压暗、去饱和，
但颜色不变——颜色是按 userId 派生的身份标识，换掉等于换了个人）。离线且一张都没标过
的不显示，免得一条用久了的分享被十几个从没动过手的受邀者撑长。留下离线贡献者是必须
的：他标过的照片还挂在网格里，条上找不到他，那些头像就成了点不动的死链接。

### 审计日志

`/admin` 里能按时间倒序翻看、按 actor 和 action 过滤，也能导出 CSV。
CSV 五列：`ts, actor, nickname, action, payload`。

**令牌在任何情况下都不写进日志**：写入前会拿这条分享的分享令牌和全部用户令牌做一次
整值替换，命中的换成 `[redacted]`。日志里只出现 `shareId` / `userId`。
导出 CSV 之后建议自己用文本编辑器打开确认一眼——这条检查在验收清单里。

**导出也留痕**（`export.run`，载荷是 `mode` / `dest` / `counts`）。这条记的是
"这次导出被接受了"，不是"它跑完了"：`counts` 是**计划**要动的张数和文件数，
一个跑到一半失败或被取消的任务同样会留下这一行。这是有意的——任务开始那一刻
才是那个可审计的决定，而正在删 RAW 的进程如果崩了，恰恰是最需要日志里有这一行
的时候。`dest` 是你磁盘上的绝对路径（审计日志只有管理员读得到）。

访客的操作只记进**他自己那条链接**的日志；管理员的操作按该文件夹下每一条活跃
链接各记一条。同一个文件夹上的两条链接不会互相抄写对方的访客 id 和昵称。

### 当前行为里几条必须先知道的事

以下都是当前代码的**实际**行为，不是设计意图的复述。写在这里，是因为撞上去再回头查
比先知道要贵得多。

**1. 撤销是当场生效的，过期不是；而且"被踢下线"这件事本身不进日志。**

撤销分享时，服务端在同一个请求里就把该分享的所有在线访客断开（先断流，再写日志）。
过期不一样：它靠每条 SSE 连接自己的心跳去发现，心跳 25 秒一次，所以**从过期时刻到访客
被真正断开，最多差一个心跳**。这段时间里他的界面还挂着，还能翻图，但他发出的任何请求
都已经在服务端被当成"无身份"拒掉了——也就是说他改不动东西，只是界面上暂时没告诉他。
（这个延迟只影响**已经连着的人**。链接一过期，新的人打开它立刻就看到
「链接不存在或已失效」，没有窗口期。）

更值得注意的是日志这一头：**无论撤销还是过期，把人踢下线的那一刻不产生任何审计记录。**
你在日志里能看到的，是那个人后来再敲门时留下的一条 `user.denied`（reason 是 `expired`
或 `revoked`），而且这条记录的 actor 是 `anonymous`——连是谁被挡在门外都对不上号。
`session.disconnect` 只在访客主动点"退出"时才记，被踢、关浏览器、断网都不记。
所以日志能告诉你"有人后来敲过门被拒了"，**不能**告诉你"他是看图看到一半被断的"。

**2. 访客的 join 路径仍然是阻塞的。**

摄影师这一侧开库已经改成非阻塞了：点开文件夹立刻返回，扫描进度走 SSE 推给界面。
访客那一侧没有：点链接进来时如果这个库还没开完，他会一直等到扫描结束才看到第一张图。
读卡器上 3000 对照片要几十秒，这几十秒里他看到的是"正在载入照片…"。

跟是谁发起的扫描无关——你刚点开文件夹、扫描还在跑，这时进来的访客一样得等到扫完。
想让客户进来就有图，先把文件夹开好、等扫完，再把链接发出去。

**3. 审计日志按 actor 过滤有个坑。**

`user.role-change` / `user.disable` / `user.enable` / `user.delete` 这四种记录，
`actor` 一律是 `admin`，而 `nickname` 字段放的是**被操作的那个人**。
服务端的过滤是严格等值匹配，只看 `actor` 这一个字段。于是：

- 按某个访客的 id 筛，只能筛出**他自己做过的事**，筛不到"管理员对他做过什么"
- 按 `admin` 筛，会把管理员对**所有人**做过的事一起倒出来，没法只看某一个人

记录里其实带着 `targetUserId`，但 API 没有开放这个过滤参数，CSV 也把它压进了 `payload`
那一列的 JSON 里。要按人追某个访客身上发生过什么，目前只能导出 CSV 自己筛。
另外注意 `nickname` 这一列在不同 action 上含义是不同的（自己做的事 = 自己的昵称；
管理员做的事 = 被操作者的昵称），别把它当成"谁干的"来读。

**4. 不做实时光标同步。「不做按用户分层的标记」现在只对*有效标记*成立了。**

看不到别人的光标、选区、正在看哪一张。

**有效标记**——也就是网格上真正显示出来的那一个——仍然是一份，冲突按"后写覆盖"处理
（服务端时间戳为准），写完向该库所有连接广播最终值。

但**每个人的每一票现在都留着**，存在 `marks.json` 的 `contrib` 表里。这就是「按客户
维度筛选」的数据来源：一张新娘收藏、被妈妈改成排除的照片，有效标记是妈妈的，而新娘
那一票仍然查得到。想要"客户初选 vs 摄影师终选"两份**各自独立的结果**再比对合并——
那仍然是另一个产品，这里没有：`contrib` 是一份历史，不是两条并行的选片流程。

**5. 在线名单按链接隔离；标记不隔离。**

同一个文件夹上可以挂多条链接（给新人一条、给父母一条）。**在线名单只给你看走同一条
链接进来的人**——父母那条链接的访客看不到新人那条链接的访客叫什么、是谁。你自己
（管理员）照常看得见全部，不管他们从哪条链接进来。

**标记是反过来的，而且是有意的**：所有人编辑的是同一份标记集，别人的改动必须实时到达
每一个人，否则两条链接的人会看到两份互相矛盾的结果——而"一起做出一份结果"正是这个功能
存在的理由。所以标记广播是全局的，不按链接过滤。

代价落在归属角标上：一张照片可能是另一条链接的人标的，而那个人不在你的名单里，
于是角标显示成「已离开的成员」加时间，字母位是个 `?`（见下一条）。

**6. 离线成员的昵称，你这一侧解析得出来，客户那一侧解析不出来。**

**你这一侧**除了在线名单，还会拉一份该文件夹下所有分享的用户名册，所以客户关掉
网页之后，他标过的那些照片上的角标**照常写着他的名字**，成员条上也还留着他（灰的）。
（这以前是个 bug：客户一走，角标当场变成 `?`、整条成员条直接消失。）

**客户那一侧**只有在线名单（SSE 推的 presence 事件），没有用户目录——那个接口是
管理员专属的。所以角标指向一个不在他名单上的人时（对方离线了，或者走的是另一条
链接），显示的是「已离开的成员」加时间，字母位是个 `?`。
色块颜色按 userId 哈希，稳定不变，所以同一个人的角标前后颜色一致，只是叫不出名字。
自己和"摄影师"（管理员）总是显示得出来。

**7. 摄影师在本地点「换文件夹」，会把在线访客的连接一起断掉——但会先问你一句。**

设计上说的是"一条活着的分享把库会话钉住，摄影师本地换文件夹不该把正在看图的客户踢下线"。
这一条**没有**实现：关闭会话确实会结束该会话上的每一条 SSE 连接，访客也在内。

实现的是其中最要紧的那一半——**你至少知道自己按下去会发生什么**。这个会话上还有访客
在线时，服务端回 409 `guests-online` 并带上人数，本地状态一个字段都不动，界面弹一个
确认框。它有三个出口，顺序就是推荐程度：

1. **去撤销链接…** —— 唯一真正结束访问的动作（见下一段）
2. **仍然关闭** —— 会把正在看图的人当场断掉
3. **取消** —— 默认。误按「换文件夹」是很常见的事

确认框里那句话也是实话的一部分：**他们会当场掉线，但手里的链接不会失效。**
关文件夹只是你这一侧脱离——客人刷新一下、或者明天再点开，只要你又打开了这个文件夹
他就又能看。要真正结束访问，得去分享面板撤销那条链接。那句话原样来自服务端，
前端一个字都不拼。

（访客那一侧具体会看到什么，仍然只在自动化测试里验证过，没在真机上确认。见验收清单。）

**8. 取消标记会回退到上一个人那一票——这是本次唯一被改变的收敛行为。**

你收藏了 IMG_0001，客户把它改成排除，客户又点一次取消。**现在这张回到「收藏」**，
角标是你；改造前它会变成「未标记」，你那一票永久消失。

理由是原来那个行为在协同下几乎总是错的：客户「取消」表达的是"我收回我的意见"，
不是"把摄影师的意见也一起抹掉"。代价是取消标记不再等价于"清空这张照片的状态"——
真要清空得每个人各取消一次，或者你自己再按一次 `U`（你那一票也被取消之后就真的空了）。

没有摄影师最终决定时，客户改判仍按协同规则更新有效标记；已有最终决定时仅更新客户原始意见。

## 验收现状

以上行为均来自单元测试与代码走查；这个项目尚未在本环境中对着一个真实的、
成千上万张照片的库跑过完整的端到端验收（长时间滚动内存曲线、真实网络环境下的
优先级抢占、真实文件系统上的大批量导出等）。

**这一条在协同阶段之后依然成立，而且要再加一句：协同功能也从未在两台真实设备之间跑过。**

自动化测试覆盖权限矩阵（四种身份 × 每一条受保护路由的状态码）、
令牌生命周期、昵称唯一性、审计日志不含令牌、并发写同一张照片时服务端的收敛结果。
这些都是**逻辑**上的断言。它们**不**证明：

- 三千张真实 RAW 从读卡器上扫描、烘焙、滚动时的表现
- 两个人同时标记时的实际体感——延迟多久算"实时"，别人的标记跳出来会不会打断自己
- 电脑浏览器中长时间选片、双图对比和鼠标框选的实际体验
