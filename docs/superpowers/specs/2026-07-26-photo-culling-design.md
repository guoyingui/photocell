# 摄影师选图程序（PhotoCull）设计文档

日期：2026-07-26
状态：已确认，待实现

## 1. 问题与目标

摄影师从相机导出一整场拍摄的照片，每张照片有一个 RAW 和一个同名 JPG。需要一个工具来快速过一遍所有照片，标出要留的和要扔的，最后把留下来的那些照片的 RAW 文件单独复制出去交付后期。

现有工具（Lightroom / Photo Mechanic）要么导入慢、要么收费。本程序只做「选片」这一件事，不做调色、不做管理、不建目录数据库。

### 成功标准

- 打开一个含 3000+ 对照片的文件夹，1 秒内可开始浏览
- 以任意速度滚动缩略图网格，不卡顿、不泄漏内存、不堆积无用请求
- 连拍序列在网格中折叠成一个格子，不淹没版面
- 键盘全流程操作，不需要碰鼠标
- 导出时不丢图、不误删

### 明确不做（YAGNI）

- 任何形式的图像编辑、调色、裁剪
- RAW 解码渲染（缩略图与预览一律来自配对的 JPG）
- 多用户、账号、云同步
- 数据库（状态就是一个 JSON 文件）
- 五星评分、色标、关键字（三态标记已覆盖选片需求）

## 2. 总体架构

本机 Node 服务 + 浏览器前端。`npm start` 启动服务并自动打开浏览器。

```
photocull/
├─ package.json              npm workspaces: server + web
├─ server/                   Node 22 + Express (ESM)
│  ├─ index.js               启动、托管 web 构建产物、开浏览器
│  ├─ routes/
│  │  ├─ fs.js               目录浏览（选文件夹用）
│  │  ├─ library.js          扫描、配对、元数据
│  │  ├─ thumb.js            缩略图与预览
│  │  ├─ original.js         1:1 查看时的原始 JPG 流
│  │  ├─ marks.js            标记读写
│  │  └─ export.js           导出任务 + SSE 进度
│  └─ lib/
│     ├─ safepath.js         路径穿越防护
│     ├─ scan.js             递归扫描、扩展名分类、stem 配对
│     ├─ meta.js             EXIF 读取（exifr）
│     ├─ thumbs.js           sharp 生成 + 磁盘缓存 + 并发闸门
│     ├─ bake.js             后台预生成队列
│     ├─ store.js            marks.json 原子读写
│     └─ transfer.js         复制 / 移动 / 校验 / 冲突处理
└─ web/                      Vite + React 19 + TS + zustand
   └─ src/
      ├─ store/              zustand: library / marks / view / undo
      ├─ lib/
      │  ├─ thumbQueue.ts    优先级队列 + AbortController + 并发闸门
      │  ├─ blobCache.ts     LRU + revokeObjectURL
      │  └─ bursts.ts        前端连拍分组（纯函数）
      └─ components/         Grid / StackCell / Lightbox / ExportPanel / FolderPicker
```

服务只监听 `127.0.0.1`，默认端口 5183（被占用则顺延）。

### 为什么后端做重活

3000 对意味着 3000 张 6000×4000 的 JPG。浏览器里逐张解码是灾难。`sharp`（libvips + libjpeg）在 resize 到 320px 时启用 shrink-on-load，直接以 1/8 尺度做 DCT 解码，单张约 8–15ms，比浏览器路径快一个数量级，且不占用 UI 线程。

## 3. 扫描与配对

### 3.1 递归遍历

从用户选定的根目录递归向下。

- 跳过：以 `.` 开头的目录、`.photocull`、`__MACOSX`、`.Trashes`、`*.lrdata`、`Lightroom Previews*`
- 深度上限 8 层，超出记录警告并停止下探
- 不跟随符号链接（避免环）
- 遍历过程中每收集 500 个文件向前端推送一次增量

### 3.2 扩展名分类

RAW（不区分大小写）：
`cr2 cr3 crw nef nrw arw srf sr2 raf orf rw2 pef ptx dng 3fr fff iiq x3f mrw kdc dcr erf mef mos srw rwl gpr`

JPG：`jpg jpeg jpe`

其余扩展名忽略（不报错，计入「已跳过 N 个非照片文件」）。

### 3.3 配对规则

- stem = 去掉最后一个扩展名后的文件名
- **配对只在同一层目录内进行**，按 stem 大小写不敏感匹配
- **资产 ID = POSIX 相对目录 + `/` + stem**，例如 `cam-a/IMG_1234`。根目录下的文件 ID 就是 stem 本身。这保证两张存储卡都含 `IMG_1234` 时不会互相覆盖标记。
- 一个资产可持有**多个 RAW**（如同时存在 `.CR3` 和 `.DNG`），存为数组，导出时全部复制
- 一个资产持有一个 JPG（同 stem 多个 JPG 时按字典序取第一个，其余计入警告）

### 3.4 孤儿处理

- **只有 RAW 没有 JPG**：仍显示为一个格子，用占位图 + 「无 JPG 预览」角标。可以标记、可以导出。
- **只有 JPG 没有 RAW**：正常显示，角标标出「无 RAW」。可以标记，但导出 RAW 时会被跳过并在导出结果里明确列出。

静默丢图是这个程序最不可接受的失败模式，所以两种孤儿都必须可见。

### 3.5 三阶段加载

每阶段结束即向前端推送，不等下一阶段：

| 阶段 | 内容 | 3000 对预估 |
|---|---|---|
| ① 遍历 | `readdir` + `stat`，分类 + 配对 | < 500ms |
| ② 元数据 | `exifr` 只解析 EXIF 段，**不解码像素**，并发 8 | 4–8s |
| ③ 烘焙 | 后台低优先队列，把全部缩略图写进磁盘缓存 | 40–90s |

阶段 ① 结束时界面即可交互，格子先显示骨架。

### 3.6 元数据字段

`exifr` 只取：`DateTimeOriginal`、`SubSecTimeOriginal`、`Orientation`、`Model`、`BodySerialNumber`、`ISO`、`FNumber`、`ExposureTime`、`FocalLength`。

`DateTimeOriginal` 缺失时依次回退到 `CreateDate` → 文件 `mtime`，并在资产上打 `timeSource` 标记（连拍分组对回退来源的资产更保守，见 §5）。

## 4. 缩略图管线

这是整个程序的性能核心，也是「快速浏览时的缓存问题」的正面解法。

### 4.1 磁盘缓存

- 缓存位置：`<root>/.photocull/thumbs/`
- 缓存 key：`sha1(相对路径 + mtimeMs + size + tier)` 前 16 位，文件名 `<hash>.webp`
- 两档尺寸：`grid` 长边 320px（q=72）、`preview` 长边 1280px（q=82）
- 响应头：`ETag: <hash>` + `Cache-Control: public, max-age=31536000, immutable`。mtime 或大小变了 hash 就变，所以可以安全地用 immutable。

第二次打开同一文件夹几乎瞬开——缩略图全部命中磁盘 + 浏览器 HTTP 缓存。

### 4.2 生成

`sharp(path, { failOn: 'none' }).rotate().resize({ width, height, fit: 'inside', withoutEnlargement: true }).webp({ quality })`

- `.rotate()` 无参数即按 EXIF Orientation 自动摆正
- `failOn: 'none'` 让截断的 JPG 也能出图（相机卡拔早了很常见）
- 生成失败时返回一个占位 SVG（HTTP 200，避免前端反复重试），并在资产上记 `thumbError`
- 服务端 `p-limit(cpus)` 闸门，防止 sharp 打满 CPU 导致整个服务失去响应

### 4.3 后台烘焙

打开文件夹后启动烘焙队列，按「先可视区、再全量顺序」把缩略图烤进磁盘。前端顶栏显示 `已缓存 1204 / 3187`。烘焙让位于实时请求：实时队列非空时烘焙暂停。

### 4.4 前端四层防御

**① 不立即请求，先入队**
瓦片进入视口时不直接 `fetch`，而是压入优先级队列。

**② 优先级 = 距视口中心的距离**
每次滚动停止（rAF 节流）重排队列。并发上限 6，对齐浏览器同域连接数。结果：停下来时眼睛正在看的那一行永远最先出图。

**③ 滚出视口立即 abort**
每个瓦片持有一个 `AbortController`，`IntersectionObserver` 报告离开视口时立刻 `abort()` 并出队。快速滚动掠过的几百张图，请求在半路被掐断——不占带宽、不堵后端队列、不浪费 CPU。**这是快速滚动不卡的关键。**

**④ LRU + 显式释放**
解码后的 blob URL 存 LRU，容量 1200。淘汰时调 `URL.revokeObjectURL()`。不释放的话滚过 3000 张会攒下数百 MB 泄漏内存。

渲染用 `<img decoding="async">`，并在插入 DOM 前 `await img.decode()`，避免解码阻塞主线程造成滚动掉帧。

### 4.5 虚拟滚动

`@tanstack/react-virtual` 做**行级**虚拟化。网格行高固定；连拍组展开时插入一个整宽的「展开行」，高度不同，由 virtualizer 的动态测量处理。上下各多渲染 2 行作为缓冲。

## 5. 连拍分组

### 5.1 判定规则

对全部资产按拍摄时间升序，相邻两张同时满足下列条件即归入同一组：

1. 时间差 ≤ 阈值（默认 1.0s）
2. **同一机身**：`Model` + `BodySerialNumber` 相同；两者都缺失时退化为「同一父目录」
3. 两张的 `timeSource` 都不是 `mtime` 回退（mtime 精度不足以判连拍）

组内 ≥ 2 张才算连拍组，否则按单张处理。

条件 2 是递归扫描带来的必要约束：多机位同时按快门时，纯时间判定会把不同相机的照片错误合并。

### 5.2 前端计算

后端只返回时间戳与机身标识，**分组在前端做一次线性扫描**。所以阈值滑块（0.3s – 5.0s）是实时重排的，不发任何请求。体育题材调到 0.5s、人像调到 2s，各自舒服。阈值存进 `marks.json` 的 settings。

### 5.3 卡牌堆展示

- 一组占一个格子，背后错开渲染两张「纸」形成层叠感
- 右上角 `×7` 角标
- 组的标记状态显示为 `2/7 已选`；组内全部收藏 / 全部排除时整组套上对应边框色
- 点击角标或组格子 → 就地展开成一个整宽行，横向平铺组内全部照片；再点收起
- 展开行内每张照片可独立标记

## 6. 标记模型与交互

### 6.1 三态

`pick` / `none` / `reject`，互斥。默认 `none`。

### 6.2 快捷键

| 键 | 动作 |
|---|---|
| `P` 或 `F` | 收藏 |
| `X` | 排除 |
| `U` | 取消标记 |
| `←` `→` `↑` `↓` | 移动选中 |
| `Enter` / 双击 | 进入全屏大图 |
| `Space` | 大图内切换 1:1 |
| `Esc` | 退出大图 / 收起展开组 |
| `1` `2` `3` `4` | 切换筛选视图 |
| `Cmd/Ctrl+Z` | 撤销 |
| `Shift+点击` | 区间多选，再按标记键批量标记 |

### 6.3 筛选视图

顶栏四个 tab，各带实时计数：**全部 / 收藏 / 排除 / 未标记**。

「先收藏、再对收藏二次排除」的流程即：切到「收藏」视图 → 按 `X` → 该张从当前视图移出（带 200ms 划出动画和一条「已排除，Cmd+Z 撤销」的 toast）。

左侧栏列出所有子目录及各自照片数，点击可只看某个子目录（与四个 tab 正交叠加）。

### 6.4 撤销

撤销栈保留最近 50 步，记录 `(assetId, 旧标记, 新标记)`。批量标记算一步。撤销不跨文件夹会话。

## 7. 状态存储

写在选定根目录下的 `.photocull/`：

```
<root>/.photocull/
├─ marks.json
├─ marks.bak.json
└─ thumbs/*.webp
```

`marks.json`：

```json
{
  "version": 1,
  "updatedAt": "2026-07-26T10:22:31.004Z",
  "marks": { "cam-a/IMG_1234": "pick", "cam-b/DSC_0088": "reject" },
  "settings": { "burstThresholdMs": 1000, "gridSize": "medium", "sort": "time" }
}
```

- key 是资产 ID（相对路径 + stem），不含扩展名，所以补拍 RAW、换扩展名大小写都不影响
- `none` 状态不写入文件，减小体积
- 写入策略：**防抖 500ms + 原子写**（写 `marks.json.tmp` → `fsync` → `rename`）。断电或强杀不会产生半个文件。
- 每次成功写入前把旧文件复制为 `marks.bak.json`
- 读取时 JSON 解析失败则自动回退到 `.bak`，并向用户明确提示

## 8. 导出

### 8.1 目标目录

服务端目录浏览器选择，或直接粘贴绝对路径，也可在选定目录下新建子目录。目标目录不得是源根目录本身或其子目录（防止导出结果被下一次扫描当成源照片）。

### 8.2 选项

| 选项 | 默认 | 说明 |
|---|---|---|
| 导出范围 | 收藏且未排除 | 三态互斥，所以等价于「所有 `pick`」 |
| 同时复制 JPG | 关 | 开启时可选是否放进 `JPG/` 子目录 |
| 目录结构 | 保留相对结构 | 或「平铺到单一目录」，冲突时加 `_1` 后缀 |
| 模式 | 复制 | 或「移动」 |
| 生成清单 | 开 | `manifest.csv` + `rejected.txt` |

### 8.3 移动模式的安全顺序

移动**不是** `rename`，而是严格的三步：

1. 复制到目标
2. 校验目标文件大小与源一致（并比对 mtime）
3. 校验通过后才删除源文件

任何一步失败立即中止整个任务，已完成的部分保留，未处理的源文件原封不动。因为顺序保证了「源文件在校验通过前不会被碰」，所以中止后的状态永远是安全的——最坏情况只是目标目录里多了些已复制的文件。

移动模式需要在对话框中**输入待移动的照片数量**才能启动。

### 8.4 冲突处理

目标已存在同名文件时：
- 大小与 mtime 都相同 → 跳过，计入「已跳过」
- 否则 → 加 `_1`、`_2` 后缀，计入「已重命名」

### 8.5 进度与结果

SSE 推送 `{ done, total, currentFile, skipped, renamed, errors }`，可中途取消（取消后不再处理新文件，当前文件处理完即停）。

完成后展示结果摘要，明确列出：
- 成功导出 N 个 RAW
- **M 个收藏的照片没有 RAW 被跳过**（孤儿 JPG）——单独高亮，这是最容易被忽略的丢图场景
- 跳过 / 重命名 / 出错各多少

### 8.6 清单文件

`manifest.csv` 列：`assetId, mark, rawFiles, jpgFile, captureTime, burstGroup, exportedAs`
`rejected.txt`：所有 `reject` 资产的 ID，每行一个。

## 9. 安全边界

服务只绑 `127.0.0.1`（不是 `0.0.0.0`），否则同网段任何设备都能读硬盘。

所有接收路径参数的接口都必须过 `safepath.js`：`fs.realpath` 解析后判断是否仍在允许的根目录内，否则 403。允许的根目录 = 当前打开的照片文件夹 + 导出目标目录 + 目录浏览器的浏览根（用户主目录及各挂载卷）。

不这么做的话，任何本地网页都能通过 `fetch('http://127.0.0.1:5183/api/thumb?path=/etc/passwd')` 读取任意文件。

## 10. 测试策略

Vitest 覆盖服务端纯逻辑：

- **scan**：同 stem 跨目录不撞车、多点文件名、大小写混合扩展名、一资产多 RAW、双向孤儿、跳过规则、深度上限
- **bursts**（前端纯函数）：空 EXIF、时间完全相同、跨机身不合并、mtime 回退不参与、阈值边界值、跨天
- **store**：原子写、模拟写入中途崩溃后仍能读出完整旧数据、损坏 JSON 回退到 bak
- **transfer**：冲突跳过与重命名、移动的校验失败中止、目标为源子目录时拒绝
- **safepath**：`../` 穿越、符号链接指向根外、绝对路径注入

前端只测 `thumbQueue`（优先级排序、abort 出队、并发上限）和 `blobCache`（LRU 淘汰、revoke 调用）。

组件不做单测。UI 正确性靠手动过一遍真实文件夹验证。

## 11. 已确认的决策记录

| 决策 | 选择 | 备选与放弃原因 |
|---|---|---|
| 运行形态 | 本地 Node 服务 + 浏览器 | 纯前端 File System Access API：仅 Chromium，浏览器解码大 JPG 上千张必卡 |
| 规模目标 | 3000 对以上 | 决定了必须虚拟滚动 + 磁盘缓存 + 后台烘焙 |
| 连拍判定 | EXIF 时间间隔，阈值可调 | 加机身约束是递归扫描带来的补充，非替代 |
| 标记模型 | 三态互斥 | 五星评分对纯选片是多余复杂度 |
| 堆叠形式 | 卡牌堆 + ×N 角标 + 点击展开 | 悬停轮播需预载组内全部缩略图，收益不抵成本 |
| 状态存储 | 照片文件夹内 `.photocull/` | 进度跟着文件夹走，换机器不丢 |
| 大图审阅 | 全屏 + 1:1 放大 | 双图对比实现量大，且卡牌堆展开已能横向比较 |
| 目录遍历 | 递归 | 用户按机位分子文件夹 |
