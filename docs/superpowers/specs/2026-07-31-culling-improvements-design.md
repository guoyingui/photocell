# 选片改进五条：文件夹可达性、缩放、刷新、隐藏、客户维度

**日期：** 2026-07-31
**状态：** 已确认，待实施

## 0. 一句话

五条需求，**一份规格一次做完**。其中 1–3 是界面手感（前端 + 服务端目录层），
4–5 是数据模型手术（`marks.json` 加两个字段、`shares.json` 加一个开关、
访客能看到什么要重新定义）。

| # | 要求（用户原话） | 落成什么 |
|---|---|---|
| 1 | 「文件夹选择，支持拖动文件夹，支持 windows 系统选择 C 盘以外的盘符」 | `browseRoots()` 在 win32 上枚举盘符；前端两处硬编码 `/` 改掉；拖拽**只用来定位**，零请求 |
| 2 | 「照片预览时支持灵活缩放，支持刷新功能」 | `gridSize` 三档枚举换成连续像素宽度 + 顶栏滑块 + ⌘/Ctrl 滚轮；顶栏加「刷新」原地重扫 |
| 3 | 「双击照片后的查看界面，支持照片灵活缩放，并在右上方增加一个关闭按钮」 | 大图连续缩放 0.5×–8×；右上角固定关闭按钮，半透明深色不砸洞 |
| 4 | 「选片支持隐藏功能……对于已经标记的照片不可进行隐藏」 | `marks.json` 加 `hidden`；**仅管理员可写、对所有人生效**；第五个 tab「已隐藏」 |
| 5 | 「分享支持设置公开/隐藏客户选片标记……管理员可以进行客户维度的筛选」 | `marks.json` 加 `contrib` 贡献表；`shares.json` 加 `showPeerMarks`；顶栏加客户下拉 |

设计问答中已明确选定、**不要再回头讨论**的五个取舍：

1. **拖拽只定位，不搜索。** 备选的「服务端指纹反查」已被否掉。
2. **隐藏只有摄影师能按，对所有人生效。** 备选的「客户也能隐」「每人各藏各的」均已否掉。
3. **客户维度要回答「新娘收藏过的那些」**，不是「最后一次是新娘改的」。
4. **隐藏客户标记时，客户仍然看得见摄影师的标记。** 只屏蔽「别的客户」。
5. **`marks` 从 `contrib` 求得**，不是各存各的。

## 1. 数据模型

### 1.1 `marks.json` 的新形状

```jsonc
{
  "version": 1,
  "updatedAt": "…",
  "marks":     { "IMG_0001": "reject" },                        // 形状不变
  "marksMeta": { "IMG_0001": { "by": "admin", "at": 1240 } },   // 形状不变
  "settings":  { "cellWidth": 210, "burstThresholdMs": 1000, "sort": "time" },

  "hidden":  ["IMG_0007", "IMG_0031"],
  "contrib": {
    "IMG_0001": {
      "u_ab":  { "mark": "pick",   "at": 1234 },
      "admin": { "mark": "reject", "at": 1240 }
    }
  }
}
```

这份示例里 `marks` 和 `marksMeta` 的值**不是随手填的**：新娘（`u_ab`）先收藏，
摄影师后来改成排除，`at` 大的赢，所以有效标记是 `reject`、归属是 `admin`。
两张表任何时候都必须满足 §1.3 的求值规则 —— 对不上就是 bug。

`marks` 和 `marksMeta` 的形状**一个字节都不改**。这不是保守，是必要条件：
导出链路、`web/src/lib/derive.ts`、乐观更新与回滚三条路径全都按现在的读法工作
（见 `server/lib/store.js` 顶部那段注释）。新东西一律走平行表。

### 1.2 `contrib`：每人每张只留最后一次

**不留完整历史。** 新娘收藏 → 取消 → 再收藏，留三条对「她收藏了哪些」这个问题
没有任何帮助，只会让文件随着选片时长无限增长。完整历史在审计日志里，
那才是它该待的地方。

**取消标记就删掉该 userId 的条目**，不写 `{mark: null}`。筛选器只有
「收藏 / 排除 / 未标记」三个值可筛，`null` 筛不出来；而「她取消了」和
「她没碰过」对这三个值来说是同一件事。

**存在 `marks.json` 而不是 `~/.photocull/`。** 三个理由里最硬的一条是：
筛选发生在库视图里，要和 `assets` 逐条对齐，放在另一个目录意味着每次筛选
都要跨两份存储做连接。

**代价必须写进 README**：交付文件夹给客户时，`marks.json` 里会带上 userId
（`u_` 开头的随机串）。**不含昵称、不含令牌** —— 昵称在 `~/.photocull/shares/<id>/users.json`
里，不跟着走。

### 1.3 `marks` 从 `contrib` 求得

```
effectiveMark(id) = contrib[id] 里 at 最大的那条的 mark
                    （contrib[id] 为空或不存在 → 无标记）
```

- **标记时**：结果和现在一模一样（后写的 `at` 最大，赢）。
- **取消时**：删掉自己那条之后重新求值，**会回退到上一个人那一票**。

回退这一条是**标记收敛逻辑里唯一被改变的行为**，而且是有意的。现在的行为是：
新娘把摄影师收藏的一张改成排除、再自己取消，摄影师那一票就永久消失了。
在隐藏模式下这尤其危险 —— 她根本看不见自己动了别人的东西。

`marks` 仍然**落盘**（不是每次读取现算）：导出、`filterAssets`、`countByTab`
都直接读它，改成派生会把一个 O(1) 的查表变成对整库的遍历。落盘的那份是
求值结果的缓存，写入路径负责让它和 `contrib` 保持一致。

`marksMeta` 相应地也从 `contrib` 求得：`by` = 求值胜出者的 userId，`at` = 它的时间戳。
两张表因此永远对得上，不需要额外的一致性检查。

### 1.4 迁移：旧文件回填 `contrib`

旧 `marks.json` 没有 `contrib`。首次读取时回填：

```
对每个有标记的 id：
  by = marksMeta[id]?.by ?? 'admin'
  at = marksMeta[id]?.at ?? 0
  contrib[id] = { [by]: { mark: marks[id], at } }
```

没归属的算 `admin` —— 那些文件夹是单机选的，标记本来就是摄影师自己按的。
`at` 缺失时用 `0`：任何后来的改动都会赢过它，这正是我们想要的。

**回填失败不阻塞开库。** 和 `marksMeta` 同一条规矩（`sanitizeMarksMeta`）：
字段坏成任何形状都只是退化成「贡献表是空的」，界面上就是筛选下拉里一个人都没有，
不报错。升级不该让摄影师昨天的选片打不开。

### 1.5 `hidden` 的不变量

用数组不用对象：它只有「在不在里面」这一个语义，没有值。

四条不变量，**服务端强制，不是界面上灰掉就算数**：

1. **只有管理员能写。** 访客的隐藏请求一律 403，和导出同一档。
2. **已标记的不能隐藏。** 服务端**过滤**掉请求里已标记的那些，响应回
   `{ hidden: [...], skipped: [...] }` 如实回报。**这一条不回 400** ——
   框选五十张里有一张收藏过就整批失败，是比部分执行更差的行为，而不变量
   在两种做法下同样成立。400 留给格式错误的请求。
3. **在「已隐藏」视图里给一张照片打标记，自动取消它的隐藏。** 否则
   「已标记 ∧ 已隐藏」这个非法状态会从后门溜进来。
4. **读取层也兜一道**：`sanitize()` 时如果一张照片既有标记又在 `hidden` 里
   （脏数据、并发、手改文件），**以标记为准**，把它从 `hidden` 剔除。
   不变量不能只靠写入层挡 —— 那假设了所有写入都经过我们的代码。

`hidden` 里指向已消失资产的条目**保留**。照片可能只是被临时移走
（这正是需求 2 说的「选片过程中移动或删除」），下次刷新它回来了，
隐藏状态应该还在。`store.js` 读文件时根本不知道 `assets` 是什么，
也没法在那一层过滤。

### 1.6 `shares.json` 的新开关

`Share` 记录加 `showPeerMarks: boolean`，加进 `PATCHABLE_FIELDS`
（`server/lib/shares.js:38`），可以随时改。

**默认 `true`（公开）** —— 那是现在的行为。升级不该悄悄改变已经发出去的链接的表现。

`root` 和 `token` 仍然不在白名单里，这一条不受影响。

## 2. 访客看到什么

### 2.1 派生规则

`showPeerMarks: false` 时，访客 U 看到的标记：

```
visibleMark(U, id) = contrib[id][U]?.mark
                  ?? contrib[id]['admin']?.mark
                  ?? undefined
```

自己的优先于摄影师的 —— 她改过的那一张，界面上要显示成她改过的样子。

`showPeerMarks: true` 时，访客看到的就是 `marks`（现在的行为，不变）。

**四个 tab 的计数也要按 `visibleMark` 算。** 漏掉这一条的后果很隐蔽：
网格里只有 3 张打了勾，顶栏却写着「收藏 12」—— 而那 9 张正是我们要瞒住她的。
计数和网格必须出自同一个派生结果。

### 2.2 必须在服务端落实

**不能只在前端过滤。** 和 viewer 角色同一个理由（README《三个入口，两种角色》
那一节说的「三道」）：前端过滤只是把东西藏起来，数据照样发到了对方的浏览器里，
打开开发者工具就看得见「妈妈收藏了哪些」。

两个出口都要按人过滤：

- `GET /api/library/marks` —— 访客拉初始快照
- 每一帧 marks 广播 —— 访客的实时更新

**广播的过滤不是「把值换掉」，是「先算她的新旧 `visibleMark`，没变就整条不发」。**
照抄有效标记发给她会直接泄露：妈妈刚收藏的那张，新娘屏幕上会当场亮起一个勾。
而只把值替换成 `visibleMark`、照发不误，泄露的是**时机** —— 她那一格在别人操作的
瞬间重渲染一次，等于告诉她「刚才有人动了这张」。所以判据是新旧值有没有变化：

- 别的访客标记 → 她的 `visibleMark` 不变（还是她自己的 / 摄影师的）→ **不发**
- 摄影师标记，而她自己没碰过这张 → 她的 `visibleMark` 变了 → **发**
- 摄影师标记，但她自己碰过这张 → 她看到的仍然是自己那一票 → **不发**

**访客写入不受影响。** 她标记时照常写 `contrib[id][U]`，`marks` 照常重新求值，
摄影师那边照常看到全部。屏蔽的只是「她能看到什么」，不是「她的操作有没有效」。

### 2.3 开关改动时

`showPeerMarks` 被 PATCH 之后，向该分享的在线访客推一个事件，客户端重拉
`GET /api/library/marks`（会拿到过滤后的那份）。两个方向都要推：
`true → false` 要把别人的标记从她屏幕上撤掉，`false → true` 要把它们放出来。

复用角色变更那条路径（README：「改完通过 SSE 立刻推给对方」）。

## 3. 需求 1：文件夹可达性

### 3.1 现状：Windows 上 C 盘以外真的够不着

`server/lib/session.js:150` 的 `browseRoots()`：

```js
const roots = [os.homedir()];
for (const dir of ['/Volumes', '/media', '/mnt']) { … }
```

Windows 上 `os.homedir()` 是 `C:\Users\<name>`，而那三个目录一个都不存在
（`readdir` 抛错被 `catch` 吞掉）。于是可浏览的根**只有 C 盘的用户目录**。
`assertWithin()` 会把 `D:\照片` 判为越界，403。

这不是「路径没填对」，是服务端根本不把 D 盘算作根。手动粘贴绝对路径也没用。

### 3.2 win32 上枚举盘符

并行探测 `A:\` 到 `Z:\`，能 `readdir` 的算一个根。

**不用 `wmic`** —— Windows 11 已经移除了它。**不起子进程** —— 一个纯 `fs` 调用
能解决的事不值得引入 `child_process` 的错误处理面。

**每个盘符单独加超时**：未插盘的光驱、断开的网络驱动器会让 `readdir` 挂很久。
整体再加一个总超时，超时的盘符跳过，不阻塞其余的。

**win32 上不要再把 `os.homedir()` 单独加进去。** 这一条是推演出来的，不是风格偏好：
`C:\` 已经是根了，再把 `C:\Users\guoyg` 也列成根，`containingRoot()` 取**最长匹配**
会返回后者，于是 `atRootBoundary()` 判定你站在边界上，**目录浏览器的「上级」按钮
当场变灰** —— 明明整个 C 盘都可浏览，你却退不出自己的用户目录。

只有在没有任何盘符根包住 homedir 时（C 盘枚举失败、权限不足）才补上它，
免得那种情况下连自己的主目录都进不去。

**不处理 UNC 路径**（`\\server\share`）。超出范围。

### 3.3 前端两处硬编码 `/`

- `web/src/lib/fsRoots.ts:15` 的 `within()`：`const prefix = root.endsWith('/') ? root : `${root}/`;`
  —— `D:\照片` 和 `D:\照片2` 会互相误判。
- `web/src/components/TopBar.tsx:62`：`root?.split('/').pop()` —— Windows 上
  整条 `D:\婚礼\小林` 会原样显示。

抽一个能吃两种分隔符的小工具（`web/src/lib/pathname.ts`），两处都改过去。
前端拿不到 node 的 `path`，所以必须自己写，也因此必须有测试。

### 3.4 拖拽：只定位，零请求

**浏览器给不了绝对路径。** `File.path` 是 Electron 才有的东西；
`webkitRelativePath` 只给到「相对于被拖入的那个文件夹」的路径；
`FileSystemDirectoryEntry.fullPath` 是一个虚拟路径（`/foldername`）。
这是「浏览器 + 本机服务」这个架构的天花板，不是写法问题。

所以拖拽的落点是**帮你定位，你点一下确认**：

1. `dragover` / `drop` 挂在 `FolderPicker` 整块上，`webkitGetAsEntry()` 取
   `entry.name`（只要目录名，不读任何文件内容）。
2. 比对「最近打开」列表里每条路径的 basename。命中 → 把那条置顶高亮，
   旁边给一个「打开」按钮。
3. 比对**目录浏览器当前已经加载的**子目录列表。命中 → 高亮那一行。
4. 都没命中 → 显示「你拖进来的是「婚礼-小林」，请在下面找到它」，
   并在之后每次目录浏览器加载新一层时继续用这个名字高亮。

第 2、3 步用的两份数据**前端手里都有**，所以这个功能不发任何请求、
不花任何搜索成本，也**永远不会静默猜错** —— 它从不替你打开任何东西。

拖进来的如果是文件而不是文件夹（`entry.isDirectory === false`），提示
「请拖入文件夹，不是文件」。一次拖进来多个文件夹时**只取第一个**并提示
「一次只能打开一个文件夹，已按「XXX」定位」—— 静默忽略其余的会让用户
以为程序没反应。

## 4. 需求 2：网格缩放与刷新

### 4.1 `gridSize` 换成 `cellWidth`

现在 `gridSize: 'small' | 'medium' | 'large'` 在类型（`web/src/types.ts:27`）、
服务端默认值（`server/lib/store.js:4`）、`Grid.tsx:12` 的 `CELL_W` 表里都存在，
**但全仓库没有任何界面能改它**。所以这条与其说是加功能，不如说是把已经存在的
东西接上一个控件 —— 顺便把粒度从三档换成连续。

- `Settings.gridSize` → `Settings.cellWidth: number`，范围钳制在 **120–420**。
- 迁移：`'small' | 'medium' | 'large'` → `150 | 210 | 290`（正好是现在
  `CELL_W` 的三个值，老文件夹的观感一格都不变）。非法值、超范围值 → 210。
- 顶栏一个滑块；网格上 **⌘/Ctrl + 滚轮**直接缩放。这个组合键**浏览器自己也在用**
  （页面缩放），所以监听必须 `passive: false` 且 `preventDefault()` —— 否则用户
  想缩网格，缩掉的是整个页面。
- 落盘走现有的 `PUT /api/library/settings`，**防抖** —— 滑块是连续拖动的，
  不能每帧发一个请求。

`Grid.tsx` 的 `cellH = Math.round(cellW * 0.75) + 26` 照常跟着算。
虚拟化的 `estimateSize` 依赖 `cellH`，`cellWidth` 一变行高全变，
**`getItemKey` 已经是按内容取键**（`rows.ts` 的 `rowKey`），所以实测缓存不会串行。

### 4.2 刷新

顶栏加「刷新」按钮，原地重扫当前文件夹。

**不退回选择器。** 旧网格继续显示到扫完 —— 这是它和「换文件夹」最重要的区别。

- 标记按 assetId 对齐保留。
- 消失的资产从 `assets` 里移除，但**它的标记留在 `marks.json` 里**。
  文件可能只是被临时移走（需求原话：「物理文件可能会在选片过程中移动或删除」）。
- 新增的照片正常出现，元数据和缩略图照常后台烘焙。
- 扫完提示「N 张已不在磁盘上 · 新增 N 张」。
- 光标 / 大图 / 选区指向消失的资产 → 清掉。这和 `view.ts` 里
  `setTab` / `setDirFilter` 清空 cursor 是同一类悬空指针问题，理由见那里的注释。
- 缩略图缓存**不清**：消失的资产的缓存留着，它回来时还能直接用。

**只有管理员能刷新。** 刷完向该库的所有连接广播一个事件，访客收到后自己重拉
`GET /api/library/assets`。访客不能发起刷新 —— 那会让所有人的视图被一个客户
的手滑重置。

**扫描失败 → 保留旧资产表**，只提示失败。这和开库失败退回选择器**不一样**：
那时手上没有任何可用数据，退回去是唯一选择；这里已经有一份能用的，清掉它是纯损失。

## 5. 需求 3：大图

### 5.1 连续缩放

现在是二值的：`zoom: boolean`，贴合或 1:1，空格和单击 stage 都能切换。

改成：

- **滚轮连续缩放，0.5× – 8×**，缩放中心跟随鼠标指针。
- 缩放 > 1 时可拖拽平移；**边界钳制**，不让图片完全拖出视口。
- **双击**在「贴合」和「1:1」之间切换。
- **空格**保持现有语义（贴合 ↔ 1:1）。
- 换图归位（`Lightbox.tsx:26` 的现有 effect 保留，`pan` 和 `scale` 一起复位）。

**单击 stage 不再切换缩放**（`Lightbox.tsx:82` 的 `onClick`）。它和拖拽平移
天然打架：拖完松手会触发一次 `click`，图片当场跳回贴合。点背景（stage 之外）
仍然关闭，那条不变。

`src` 的选择规则要跟着改：现在是 `zoom ? originalUrl : thumbUrl('preview')`，
改成按 `scale` 阈值切（>1 用原图）。

### 5.2 右上角关闭按钮

`position: fixed`，右上角。半透明深色圆底 + 白色 ✕ + `backdrop-filter: blur`，
默认 `opacity: .5`，`hover` / `focus-visible` 升到 1。

深色半透明在亮图和暗图上都读得出来，也不会像纯白或纯色块那样在画面上砸一个洞
—— 这是需求原话「按钮颜色最好不要影响图片查看」的落点。

**底部信息条里那个「关闭」去掉**（`Lightbox.tsx:96`）。两个关闭按钮是冗余，
而右上角是所有人在看图时找关闭的第一个地方。`Esc` 照常。

按钮要有 `aria-label="关闭"`。

## 6. 需求 4：隐藏

### 6.1 入口

角标右下角已经挤了 ✓ 和 ✕ 两个按钮（`Thumb.tsx:117`），再塞一个按钮会使操作过于密集。
所以隐藏的入口是：

- **键盘 `H`** —— 隐藏 / 取消隐藏。
- **顶栏选区操作条上的「隐藏」** —— 这是主要用法。一次清掉几十张废片，
  逐张点是不现实的。
- 大图里也可以按 `H`。

`H` 的作用对象和 `P` / `X` 完全一致 —— 走 `useKeyboard` 里同一个
`markTargets`（有选区就是整个选区，否则是光标那一张）。

**一批里混着已标记的照片时，隐藏未标记的那些，跳过已标记的**（§1.5 不变量 2：
服务端过滤 + 回报 `skipped`，不是 400），并按响应提示「已隐藏 N 张，
M 张因为已有标记被跳过」。整批拒绝是更差的选择：框选五十张里有一张收藏过，
就什么都做不了。

单张已标记的照片按 `H` 时 `skipped` 里只有它，提示「已标记的照片不能隐藏，先取消标记」。
**这条提示必不可少** —— 一个按了没反应的快捷键和一个坏掉的快捷键无法区分。

访客那一侧**整个入口不渲染**（不是置灰），和 viewer 角色同一条规矩。

### 6.2 「已隐藏」视图

tab 栏加第五个：**「已隐藏 N」，快捷键 `5`，仅管理员可见**。

在这个 tab 里每张图有「取消隐藏」按钮。在这里给一张照片打标记会自动取消隐藏
（§1.5 不变量 3）。

`FilterTab` 类型加 `'hidden'`。

### 6.3 隐藏对其它视图的影响

隐藏的照片**不进**：网格、四个 tab 的计数、大图翻页顺序、导出。

导出那一条是**天然成立**的（隐藏的必然未标记，而导出只导收藏的），但
**仍然要在 `filterAssets` 那一层显式挡住**，不能依赖这个巧合 —— 巧合会随着
下一次需求变更悄悄失效，而失效的那一刻没有任何东西会报错。

`derive.ts` 的改动点：

- `filterAssets`：`tab !== 'hidden'` 时排除 `hidden` 集合；`tab === 'hidden'` 时只留它们。
- `countByTab`：先剔除 `hidden` 再统计四个数，另外单独返回 `hidden` 的数量。
- `dirCounts` / `dirRejected`：**同样要剔除** —— 否则左侧目录会显示
  「这个文件夹 30 张」而网格里只有 12 张。

## 7. 需求 5：客户维度筛选

### 7.1 下拉

tab 栏右边一个下拉：`所有人 ▾ / 摄影师 / 新娘小林 / 妈妈 / …`

选中某个人之后，**全部 / 收藏 / 排除 / 未标记**四个 tab 的含义变成
「在这个人的贡献里」：

- 全部 = 他碰过的（`contrib[id][U]` 存在）
- 收藏 / 排除 = 他那一票是 pick / reject
- 未标记 = **他没碰过的**（`contrib[id][U]` 不存在）

**这时候「全部」不再等于整库**，而是等于「收藏 + 排除」。看起来像 bug，其实是
需求原话要的东西 —— 「在全部页签下进行客户维度的筛选」，如果全部不受筛选影响，
那个页签下的下拉就是个摆设。数字对不上的疑虑由文案消解：筛了人之后，
「全部」这个 tab 显示成**「新娘碰过的 N」**，不再叫「全部」。

「已隐藏」tab 不受它影响 —— 隐藏是摄影师的操作，没有客户维度。

**这个下拉只筛选，不改变标记的身份。** 筛着「新娘」的时候按 `P`，记进
`contrib` 的仍然是 `admin`（你自己），不是新娘。没有任何入口能代替别人投票 ——
那会直接毁掉审计的价值，和 README 里「昵称只是显示名」那条是同一个道理。

**仅管理员可见。** 访客那一侧整个下拉不渲染。

### 7.2 名字从哪来

客户端现在只有一份在线名单（SSE 推的 presence），离线的人解析不出来
（README《当前行为里几条必须先知道的事》第 6 条）。筛选下拉必须列出
**所有贡献过的人**，包括早就离线的。

加一个 admin-only 端点，按当前库的 root 返回该文件夹下所有分享的
`userId → nickname` 映射。管理员本来就读得到 `~/.photocull/shares/*/users.json`
（审计日志页面已经在读了），不新增任何权限。

**令牌不进这个响应**，只有 `id` 和 `nickname`。

解析不出来的 userId（用户记录被删过）显示成「已离开的成员」+ 色块，
和 `Thumb.tsx` 现有的 `GONE_NAME` 逻辑保持一致，色块颜色同样走
`avatarColor(userId)` 哈希 —— 同一个人在成员条、角标、筛选下拉里必须是同一个颜色。

### 7.3 筛选是纯前端的

`contrib` 已经随 `GET /api/library/marks` 整份到了管理员手里，筛选不发请求。

按 §1 的设计，这里没有性能陷阱：`contrib` 的规模是「被碰过的照片数 × 参与人数」，
在一场三千张的婚礼里参与人数是个位数。但筛选结果仍然要**记忆化**，
和 `TopBar.tsx` 的 `countByTab` 同一个理由 —— 光标移动不该重跑全库扫描。

## 8. 错误处理与边界

| 情况 | 行为 |
|---|---|
| 旧 `marks.json` 没有 `contrib` | 用 `marks` + `marksMeta` 回填，没归属的算 `admin`（§1.4） |
| `contrib` / `hidden` 字段坏成任何形状 | 退化成空表，不报错，不阻塞开库 |
| 一张照片既有标记又在 `hidden` 里 | 读取层以标记为准，从 `hidden` 剔除（§1.5） |
| `hidden` / `contrib` 指向已消失的资产 | 保留。文件可能回来 |
| `contrib` 指向已删除的用户 | 保留，显示「已离开的成员」。筛选下拉照常列出 |
| 访客尝试隐藏 | 403，和导出同一档 |
| 隐藏一张已标记的照片 | 服务端过滤掉它，响应回报 `skipped`；不是 400（§1.5） |
| 刷新时扫描失败 | 保留旧资产表，只提示（§4.2） |
| 盘符 `readdir` 超时 / 无权限 | 跳过该盘符，不阻塞其余（§3.2） |
| 拖入的是文件不是文件夹 | 提示「请拖入文件夹，不是文件」 |
| `cellWidth` 超范围 / 非数字 | 钳制到 120–420，非法值回落 210 |
| `showPeerMarks` 改动时访客在线 | SSE 推事件，客户端重拉 marks（两个方向都推） |

## 9. 测试

**纯逻辑（node 环境，`web/src/**/*.test.ts` + `server/**/*.test.js`）**

- `contrib` 求值规则，**含取消后回退到上一个人**这一条
- 迁移回填：有 `marksMeta` 的、没有的、字段坏掉的
- `hidden` 不变量的双向兜底：写入层过滤 + 读取层剔除
- `showPeerMarks: false` 的按人过滤：自己的 > 摄影师的 > 无
- Windows `basename()` / `within()`：两种分隔符、`D:\照片` vs `D:\照片2`
- 拖拽定位的匹配：命中最近打开、命中当前目录、都没命中
- `cellWidth` 的迁移与钳制

**服务端**

- 隐藏写入的权限矩阵（四种身份 × 隐藏端点的状态码）
- 混合批次的隐藏：未标记的进 `hidden`、已标记的进 `skipped`、**响应不是 400**
- 广播过滤：别的访客标记 → 不发；摄影师标记且她没碰过 → 发；摄影师标记但她碰过 → 不发
- `showPeerMarks` 的 PATCH 进了白名单，`root` / `token` 仍然没进
- 刷新端点：管理员 200 / 访客 403
- 盘符枚举在非 win32 上不改变现有行为

**组件（jsdom，`web/src/**/*.test.tsx`）**

- 第五个 tab 和客户筛选下拉**只对管理员渲染**（访客侧整个不在 DOM 里，不是置灰）
- 大图右上角关闭按钮存在且有 `aria-label`；底部那个已经不在
- 缩放滑块改动会（防抖后）发出 `PUT /api/library/settings`

**三条门禁照常**：`npm test` / `npx tsc --noEmit` / `npm run build`。
